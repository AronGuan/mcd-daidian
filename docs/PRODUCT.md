## 0. 一句话

**替别人点麦当劳时，你手里的不是菜单，是一堆你不能违反的约束。**

麦麦代点把「关系 + 健康 + 忌口 + 预算」翻译成一份**能点、能改、能交代**的单子 —— 输出三件东西：给点餐人的餐单、给店员念的特制清单、给收餐人的说明卡。

## 1. 为什么做这个

### 1.1 供给现状（基于 184 个参赛项目的全量统计）

我们对本次大赛 215 条报名 Issue（去重后 184 个真实项目）做了完整分类：

| 用户群 | 现有项目数 | 平均 Star |
|---|---:|---:|
| 高频省钱党 | 45 | 2.91 |
| 健康管理人群 | 22 | 1.45 |
| 情绪社交 | 20 | 0.95 |
| 晒图/自我认知 | 17 | 3.29 |
| 多人组织者 | 16 | 5.19 |
| 会员资产持有者 | 13 | 3.38 |
| 情报囤积者 | 12 | 2.17 |
| 时间稀缺型 | 10 | 3.10 |
| **特殊人群（儿童/长辈/视障/过敏）** | **5** | **7.00** |

**184 个项目里，"给自己点"占 182 个。**

### 1.2 一个被系统性忽略的能力

我们逐字检索了全部 184 份报名正文，**只有 6 个项目真正使用了 `query-meal-detail` 的配料可增减（modification）能力**：

| Issue | 项目 | 用途 | 服务对象 |
|---|---|---|---|
| #26 | mcd-meal-planner | 去酱减钠建议 | 自己 |
| #70 | mcd-no-pickle | 强制去除酸黄瓜 | 自己 |
| #90 | mcd-diet-guard | 八类人群阈值改配 | 自己 |
| #123 | mcd-safe-bite | 饮食限制可行性判定 | 自己 |
| #125 | mcd-mcmate | 套餐换购特制（顺带） | 自己 |
| #162 | mcd-a11y-order | 生成店员可执行特制清单 | 自己（视障） |

**6 个全部是"给自己点"，没有一个服务于"替别人点"。**

而 `query-meal-detail` 恰恰是麦当劳 MCP 唯一能"改菜"的能力。**别人的忌口不是营养问题，是配料问题** —— 营养表只能告诉你"这菜有多少钠"，只有 modification 能告诉你"这菜能不能去掉酱"。

### 1.3 真实调用验证（本项目的技术地基）

`query-meal-detail(code=1406, storeCode=1450713)` 真实返回：

```json
{
  "code": "1406", "name": "板烧鸡腿堡", "supportModify": true,
  "modification": { "items": [{ "maxValues": 2, "minValues": 0, "values": [
    { "code": "102201", "price": 0, "name": "烤味酱",
      "selectedKey": "0-1", "unselectedKey": "0-0" },
    { "code": "120512", "price": 0, "name": "切块生菜",
      "selectedKey": "0-1", "unselectedKey": "0-0" }
  ]}]}
}
```

结论：**「去掉烤味酱」是一个真实可执行、且不加价（`price: 0`）的操作**。`unselectedKey: "0-0"` 就是"不选"的传参。

## 2. 目标人群与痛点

### 2.1 主用户：替家人点餐的中青年子女 / 家长

**典型场景**：给爸妈点、给孩子点。到店自取后带回家。

**痛点（按强度排序）**：

| # | 痛点 | 现状 | 为什么现有产品解决不了 |
|---|---|---|---|
| P1 | **我不知道他的忌口能不能被满足** | 全靠猜，或者到店问店员 | 只有 `query-meal-detail` 能回答"这道菜能不能去掉某配料"，而没人把它用在代点场景 |
| P2 | **健康约束算不出来** | 只知道"少油少盐"，不知道具体差多少 | 营养表有钠/热量，但没人把它翻译成"这顿超了多少" |
| P3 | **交代不清** | 到店只能口头跟店员描述，容易漏 | 缺一份**可直接念给店员**的清单 |
| P4 | **收餐人不知道你为什么这么点** | 家里人觉得你乱点 | 缺一份可发微信的说明 |
| P5 | **父母不会用手机点餐** | 只能子女代点 | 官方 App 的交互对长辈不友好 |

### 2.2 次用户：企业的行政 / HR / 组局人

同一套约束翻译能力可用于多人场景（谁不能吃什么），但优先度低于主用户。

### 2.3 明确不服务的用户

- **高频省钱党**：他们自己最会算，且已有 45 个项目服务
- **情绪社交用户**：伪需求 —— 该群体 20 个项目，平均 Star 仅 0.95（全场唯一低于 1）

## 3. 解决方案

### 3.1 核心循环

```
输入人物卡（关系 + 健康 + 忌口 + 预算 + 软偏好）
   ↓
三级约束翻译
   ↓
菜单筛选 → 配料改写 → 营养校验 → 价格核验
   ↓
输出三件套：餐单 / 特制清单 / 说明卡
```

### 3.2 三级约束翻译

| 级别 | 类型 | 处理策略 |
|---|---|---|
| **硬约束** | 过敏、宗教、明确不吃某样 | 先尝试用 modification **去掉**该配料；去不掉就**换菜**，并说明为什么换 |
| **健康约束** | 血压、血糖、控糖控钠 | 用 `list-nutrition-foods` 校验阈值，超标项标注超出幅度 |
| **软偏好** | 爱吃辣、爱吃板烧 | 仅影响排序，不做硬过滤 |

### 3.3 三件套交付物

**① 餐单** —— 每道菜标注「改写了什么」，并给出营养合计与达标状态。

**② 特制清单** —— 大字号、可直接念给店员。形如：

```
1  板烧鸡腿堡
   不要酱
2  玉米杯
   正常
```

**③ 说明卡** —— 可复制发微信，含营养结论、改写说明和取餐码。

### 3.4 与现有项目的差异

| 对比对象 | 它做什么 | 我们做什么 |
|---|---|---|
| mcd-send-a-meal（5★） | 收件人**营养约束** + 异地**外送** | 收件人**配料改动** + 到店**自取**（父母多数不用手机，外卖不实用） |
| mcd-a11y-order（1★） | 同样生成特制清单，但入口是**视障用户自用**（受众最窄） | 同一能力，换到**替家人点**的大众场景 |
| mcd-no-pickle（2★） | 固定去酸瓜（单一忌口） | 任意忌口的**动态约束求解** |

## 5. MCP 集成方案

### 5.1 工具链路

| 步骤 | 工具 | 用途 | 是否必需 |
|---|---|---|---|
| 1 | `query-nearby-stores` | 定位门店，拿 storeCode | 必需 |
| 2 | `query-meals` | 拉真实在售菜单与价格 | 必需 |
| 3 | **`query-meal-detail`** | **拿配料可增减结构（核心）** | **必需** |
| 4 | `list-nutrition-foods` | 营养阈值校验 | 必需 |
| 5 | `calculate-price` | 券后真实核价 | 必需 |
| 6 | `delivery-query-stores` | 外送场景的门店 | 可选（MVP 不做外送） |

### 5.2 套餐子项的处理

套餐（如「板烧鸡腿堡三件套」）的配置在 `rounds[].choices[]` 里，每个 choice 也可能带 `supportModify` 与自己的 `modification`，需递归处理。

### 5.3 特调传参规则（官方文档明确要求，必须遵守）

对包含 `unselectedKey` 的特调组：
- 选中的项：传 `selectedKey` 作为 key
- 未选中的项：传 `unselectedKey` 作为 key
- **该组内所有特调项都必须传入**

漏传未选中项会导致算价错误。这是本项目最容易踩的坑，已在原型中实现完整传参。

## 6. 数据边界与诚实声明

**这一节是产品可信度的来源，不是免责套话。**

### 6.1 已知的三个官方数据缺口

| 缺口 | 实测证据 | 我们的处理 |
|---|---|---|
| **营养表滞后于菜单** | 有人实测某门店 128 个在售餐品仅 28 个能匹配营养表（21.9%） | 每个餐品标注营养匹配状态：精确 / 存疑 / 无数据。**存疑项不参与阈值硬判定** |
| **营养表为"标准配方"值** | 板烧鸡腿堡标准配方钠 1041mg；去酱后官方不提供新数值 | 改写项标注「已改写」，但**明确声明不量化改写后的营养变化** |
| **营养接口无过敏原字段** | `list-nutrition-foods` 只返回能量/蛋白/脂肪/碳水/钠/钙六项 | 结论限定为「**配料层面能否规避**」，**不承诺医学安全**，涉花生/坚果/麸质等高危过敏一律提示咨询门店 |

### 6.2 产品内固定展示的声明文案

> 本工具基于麦当劳官方 MCP 的公开数据做配料层面的规划，**不构成医疗、营养或过敏安全建议**。
> 营养值为官方标准配方数值，配料改动后的实际数值官方未提供，故不做量化承诺。
> 如有严重过敏或慢性病，请以门店现场确认为准。

## 7. 技术架构

```
浏览器（原型：单文件 HTML；正式版：Vite + React + TS）
   ↕ HTTP
Go 服务（持 MCP_TOKEN 环境变量）
   ├── 只读快照缓存（每店每小时刷新一次菜单 + 营养表）
   ├── 约束求解器（硬约束过滤 → 组合枚举 → 营养打分）
   └── 卡片渲染
   ↕ Streamable HTTP
麦当劳 MCP（https://mcp.mcd.cn）
```

### 三条硬规矩

1. **Token 绝不进前端代码** —— 一切经服务端代理，读环境变量
2. **只调只读工具** —— 不用 `create-order` / `auto-bind-coupons` 等写操作
3. **下单交给 Skill 形态** —— Web 端只输出"可复制的下单指令"，由玩家在 WorkBuddy 里确认执行

### 缓存策略

门店菜单与营养表变化频率低（菜单按日活动、营养表近乎静态），**每店每小时拉一次**即可。
按 1000 DAU 估算，MCP 调用量约 **24 次/店/天**，与用户量无关 —— 这是把"读扩散"压成"写一次"的关键设计。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 营养表与菜单对不齐（实测覆盖率可能仅 ~20%） | 大量餐品无营养数据，无法做阈值判定 | 匹配状态可见化；无数据项降级为「仅供配料改配，不做营养宣称」 |
| 去酱后的营养真实变化无法验证 | 可能给出误导性的健康暗示 | 明确声明不量化；只做定性说明 |
| 严重过敏场景的责任风险 | 法律与伦理风险 | 高危急过敏（花生/坚果/麸质）直接提示咨询门店，产品不输出结论 |
| 门店菜单随时段变化 | 早/正/夜市菜单不同，方案可能失效 | 下单前用 `calculate-price` 实时核价，价格变动则重新求解 |
| 与 mcd-send-a-meal 场景相近 | 差异化不足 | 明确聚焦"到店自取 + 配料改写"，不做外送 |
