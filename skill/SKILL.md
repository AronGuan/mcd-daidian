# 麦麦代点

## 这个 Skill 解决什么

替别人点餐的人手里不是菜单，是一堆不能违反的约束：别人的过敏、宗教饮食、慢性病、口味。**营养表只能告诉你"这菜有多少钠"，只有 `query-meal-detail` 能告诉你"这菜能不能去掉酱"。**

这个 Skill 的核心是**配料级改写**，不是营养计算。

## 何时使用

用户表达"给某人点"的意图时触发：

- 「帮我妈点个麦当劳，她高血压」
- 「给孩子点一份，别太甜」
- 「帮同事带一份，他不吃牛肉」
- 「给我爸点，他糖尿病，预算 40」

**不适用**：用户给自己点餐（那是常规点餐，不需要约束翻译）。

## 工作流

### 第 1 步：收齐人物卡（一次性问完，不要逐条追问）

如果用户没说全，用**一次提问**收齐这五项：

| 项 | 说明 | 缺省处理 |
|---|---|---|
| 给谁点 | 关系（妈/爸/孩子/朋友/同事） | 必问 |
| 硬禁忌 | 过敏、宗教、明确不吃某样 | 无则默认无 |
| 健康约束 | 血压/血糖/控糖，或直接给钠、热量上限 | 无则默认不限制 |
| 预算 | 这一餐的上限 | 无则默认 ¥50 |
| 软偏好 | 他平时爱吃什么 | 无则不指定 |

### 第 2 步：拉门店与菜单

```
query-nearby-stores  (searchType=2, city, keyword, beType=1)
   → 拿到 storeCode
query-meals          (storeCode, orderType=1, beType=1)
   → 拿到在售餐品与 productCode
```

### 第 3 步：拿配料结构（核心步骤）

对候选主餐逐个调用：

```
query-meal-detail    (storeCode, orderType=1, beType=1, code=productCode)
```

从返回的 `modification.items[].values[]` 里读出每个配料的 `name` 与 `selectedKey` / `unselectedKey`。

**判据**：`unselectedKey` 不为空 = 该配料可以去掉。

### 第 4 步：营养校验与核价

```
list-nutrition-foods  → 按餐品名匹配营养（能量/蛋白/脂肪/碳水/钠/钙）
calculate-price       → 带特调传参做真实核价
```

营养匹配时**必须标注匹配状态**：精确匹配 / 存疑（份数或规格不确定） / 无数据。
存疑项不参与阈值硬判定。

### 第 5 步：输出三件套

见下方「输出格式」。

## 特调传参规则（最容易出错，必须遵守）

官方文档明确要求：**对包含 `unselectedKey` 的特调组，该组内所有特调项都必须传入算价与下单接口。**

- 用户**保留**的配料：传 `selectedKey` 作为 key
- 用户**去掉**的配料：传 `unselectedKey` 作为 key

漏传未选中的项会导致核价错误。例如板烧鸡腿堡的特调组有「烤味酱」和「切块生菜」两项：

```json
{ "values": [
  { "code": "102201", "key": "0-0", "quantity": 1 },   // 去掉烤味酱 → 传 unselectedKey
  { "code": "120512", "key": "0-1", "quantity": 1 }    // 保留生菜   → 传 selectedKey
]}
```

另外两条规则：
- 套餐的子项在 `rounds[].choices[]` 里，每个 choice 也可能带自己的 `modification`，需要递归处理。
- 当特调组 `minValues=1 && maxValues=1` 且 `values` 只有 1 项时，该项为**必选**，不得向用户提供"不选"的选项。

## 输出格式

必须输出三样，缺一不可。

### ① 给点餐人的餐单

每道菜标出**改写了什么**，这是可信度的来源，不能省。并给出「合计 / 钠 / 热量·蛋白」三项与限额对比。

### ② 给店员看的特制清单

大字号、可直接念。格式：

```
1  板烧鸡腿堡
   不要烤味酱
2  玉米杯
   正常
```

**没有任何改写的餐品也要列出来并标「正常」** —— 店员需要完整的对照。

### ③ 给收餐人的说明卡

可复制发微信，包含：点了什么、营养结论、为什么这么改、取餐方式。

## 边界与禁止事项

### 必须声明的三件事

1. **不构成医疗、营养或过敏安全建议。**
2. **营养值为官方标准配方数值。** 配料改动后的实际数值官方未提供，因此去酱等操作只能标为**定性改善**，不得给出量化承诺（例如不能说"去酱后钠降 200mg"）。
3. **官方营养接口不含过敏原字段。** 涉及花生、坚果、麸质等高危过敏，结论必须限定为"配料层面能否规避"，并提示以门店现场确认为准，不得输出"可以放心吃"这类结论。

### 禁止

- 禁止编造营养数值。匹配不到就如实说"无数据"，不得填 0 或估算。
- 禁止使用写操作工具（`create-order` / `auto-bind-coupons` / `draw-lottery`）。本 Skill 只做规划，下单由用户确认后另行处理。
- 禁止在输出中携带 Token、账号、订单号等敏感信息。

## 与相近项目的差异（供 README 引用）

- 与「营养约束配餐」类项目不同：那些算的是钠多少毫克，本 Skill 改的是配料能不能去掉。
- 与「异地代送」类项目不同：本 Skill 聚焦**到店自取**——父母多数不会用手机，外卖不实用；交付物是取餐码 + 特制清单，由子女去取。
- 与「视障无障碍点餐」不同：同样是生成特制清单，但本 Skill 服务的是**替家人点**的大众场景，而非视障用户自用。
